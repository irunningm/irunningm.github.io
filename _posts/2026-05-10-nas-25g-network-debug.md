本来以为是个十分钟的事——买个 USB 2.5G 网卡，插上 NAS，跑满速。结果从晚上九点折腾到凌晨一点，遇到了 USB 断连、驱动报错和网口速率异常。当时对原因做过一些判断，后来有了新的结果，这次把过程和修正一起留下。

<!--more-->

> **2026 年 9 月 26 日更新**：NAS 的 USB 2.5G 网卡已经停用。后来我剪掉旧水晶头、重新压接，网络实现了千兆。原文把速率异常直接归因于路由器 PHY、交换芯片，并据此建议购买交换机，证据不足，已在下文修正。USB 网卡掉线的具体原因仍未确认，重新压接后的结果也不能解释当时所有 USB 报错。

当前的设备与分工见 [《给家里的设备分个工》]({% post_url 2026-09-26-a-home-for-my-development-environment %})。下文保留的是五月那次排障记录，涉及版本和连接状态的描述均以当时为准。

## 背景

我有一台群晖 DS918+，原生只有两个千兆网口。最近 PC 升级了 2.5G 网卡，想让 NAS 和 PC 之间跑满 2.5G 内网速度，于是买了个 USB 2.5G 网卡（Realtek RTL8156B）。

路由器是小米 BE6500 Pro，全 4 口 2.5G，看起来完美适配。

## 第一阶段：8156B 插上去，灯不亮

把 8156B 插到 NAS 的 USB 3.0 口，驱动装好，`ip link` 能看到 `eth2`。但网线一插上去，网口指示灯就灭了。

路由器那边 `swconfig` 显示对应端口 `link:up speed:2500baseT`——路由器认为链路通了。但 NAS 侧 `ethtool eth2` 显示 `Link detected: no`。

**路由器看到链路了，8156B 自己不认。**

查 `dmesg`，发现一堆错误：

```
r8152 2-2:1.0: read type=0x0133 fail -71
r8152: Stop submitting intr, status -71
usb 2-2: USB disconnect, device number 2
usb 2-2: new SuperSpeed USB device number 3
```

USB 通信反复断连（错误码 `-71 = EPROTO`），驱动每次重新加载都失败。当时我怀疑过 USB 供电问题，但现有记录不足以确认或排除这个原因。

## 第二阶段：驱动崩溃

试着卸载重装驱动：

```bash
sudo rmmod r8152
sudo modprobe r8152
# modprobe: FATAL: Module r8152 not found
```

群晖的 r8152 是通过套件安装的，不在标准内核模块路径里。找到了真实路径：

```bash
/volume1/@appstore/r8152/r8152/r8152.ko
```

用 `insmod` 全路径加载后，驱动起来了，但 `ifconfig eth2 up` 报错：

```
SIOCSIFFLAGS: Cannot allocate memory
```

dmesg 里还有 `free_all_mem` 的内核 WARNING。这时候我怀疑是驱动版本太旧（v2.20.1），决定升级。

## 第三阶段：驱动升级，越升越乱

从 GitHub 的 [bb-qq/r8152](https://github.com/bb-qq/r8152) 项目下载了当时尝试的 v2.21.4-1（`_7.3` 版本），通过 `synopkg` 安装。结果 `synopkg start r8152` 直接失败，dmesg 里同样的 `free_all_mem` 崩溃。

我也查过项目里的 [#619](https://github.com/bb-qq/r8152/issues/619) 和 [#620](https://github.com/bb-qq/r8152/issues/620)，尝试寻找排查线索。不过，他人的报告不能直接证明我这里是同一个原因。

回退到 v2.20.1，还是同样的 `Cannot allocate memory` 错误。

当时我把怀疑转向了反复装卸驱动后的运行状态。回头看，这仍然只是一个推测；相同报错在不同版本出现，并不能单独确认根因。

## 第四阶段：重启后暂时恢复

一咬牙 `reboot`。重启后：

- v2.20.1 加载正常，无报错
- 升级到 v2.21.4 也正常，无崩溃
- eth2 成功 UP，`Link detected: yes`，`Speed: 2500Mb/s`

重启后链路暂时恢复了，但后面仍然出现掉线。这能说明一次重启改变了运行状态，还不足以证明具体是哪一环出了问题。

## 第五阶段：网口速率异常

排查过程中，PC 接在 LAN 2 口时只协商到 100M，换到 LAN 3 口仍是 100M。PC 使用 RTL8125 2.5G 网卡，当时的工具输出显示支持 2500baseT。

经过重新插拔和重启，记录里曾出现恢复到 2500M 的状态。路由器管理页面与 `swconfig` 的显示也曾不一致：一个显示 1000M，另一个显示 2500M。

原文据此把问题归因于 BE6500 Pro 的 PHY 自动协商不稳定，进一步写出了交换芯片“4 口共享 5Gbps”的判断。但当时没有足够的对照测试，也没有验证实际转发路径与吞吐量。这些判断不应当作已经证实的硬件缺陷，界面显示差异也不能单独确定故障来源。

现在能补上的实际结果是：重新压接水晶头后，网络实现了千兆。因此，这次经历里，线缆端接是必须认真检查的一环。至于 USB 2.5G 网卡的问题，需要另行看待。

## 遗留的坑：8156B 随机掉线

跑通 2.5G 后没多久，8156B 又掉了。`dmesg` 里同样的 `-71` (EPROTO) USB 协议错误，驱动反复崩溃重连。

当时的记录是重启后能工作一段时间，随后又出现错误。现有信息不足以区分网卡硬件、USB 连接、驱动或其他兼容性问题。后来我停用了这块网卡，没有继续完成定位。

排查期间，NAS 的原生千兆口作为备用管理通道保留着；USB 网卡掉线时，仍能从这个入口登录。

## 后来怎样了

目前，NAS 的 USB 2.5G 网卡已经停用。我剪掉旧水晶头、重新压接后，网络实现了千兆。

这是这篇文章最值得补上的结果。五月的排障记录里曾短暂出现 2500M，也留下了不少错误日志；这些历史现象不能直接描述今天的网络，更不能据此认定必须添置一台 2.5G 交换机。

## 这次记录能确认什么

| 观察到的事情 | 当前可以得出的结论 |
| --- | --- |
| USB 网卡出现 `-71` 错误并掉线 | 当时确实发生了连接异常，具体原因尚未定位 |
| 重启后网卡暂时恢复 | 重启后状态发生了变化，不能据此确定根因 |
| 网口速率曾落到 100M | 当时链路状态异常，不能直接认定是路由器缺陷 |
| 重新压接水晶头后实现千兆 | 端接检查是这次排障遗漏的重要步骤 |
| USB 2.5G 网卡后来停用 | 当前设备方案不再依赖这块网卡 |

以后再遇到类似问题，我会先留下连接方式、日志和每一步操作后的结果，尽量一次只改变一个条件。特别是换口、换线、重新做接头和重启这些动作，要分开记录，才能知道到底是哪一步带来了变化。
